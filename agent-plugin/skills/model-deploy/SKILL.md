# COM3D2 モデル反映

検証済みの出力を導入先へコピーし、依頼に実機反映が含まれる場合は再読み込みと表示確認まで行う。ファイルをコピーしただけで「ゲーム内に反映済み」としない。

## 対象と導入先の確定

- プロジェクトの設定・直近の出力検証・manifest を確認する。最新の編集結果が出力済みかを調べ、古い model を「最新版」として導入しない。未出力ならプロジェクト既存の出力手順を使う。
- ゲームが動いている場合は `ping` で `gameDir` とメインスレッドの生存を確認する。導入先はプロジェクト設定と既存ファイルから決める。ドライブ、作者フォルダー、ファイル名、メイド番号、装備スロットを過去の実例から固定しない。
- 衣装は `scene_info` / `list_maids` と実際の装備を調べ、対象メイド・menu・MPN・TBody スロットを確定する。ストック番号と表示中メイドの番号は一致するとは限らない。対象衣装を着用中のメイドを優先し、候補が複数で特定できない場合だけ対象を確認する。
- 依頼の範囲:
  - 「ゲームへ反映」は、必要な導入先へのコピーと対象の再読み込みを含む
  - 既に依頼されている操作について、重ねて承認を求めない
  - スキルの作成・手順の説明だけなら、ゲームへ触れない
  - セーブ、再起動、他衣装の変更を自動で追加しない

## 導入

1. model / mate / menu / tex の参照と出力ハッシュを確認する。新しい材質枠、menu のマテリアル変更命令、同梱画像を一組として扱う。ゲーム標準テクスチャへの参照は、検証された名前だけを外部依存として記録する。
2. 既存の同名 MOD がどこにあるかを確認する。別フォルダーへの二重導入で検索順に依存する状態を作らない。更新前の対象ファイルとハッシュを、ゲームの Mod 検索対象外の作業フォルダーへ退避する。
3. 対象の許可リストだけをコピーし、導入後の SHA-256 を照合する。Blend、抽出 PNG、バックアップ、途中データを導入先へまとめてコピーしない。無関係なファイルを削除・ミラー同期しない。
4. ファイルアクセス権限を守る。導入先への書き込みに権限が要るなら、利用中のエージェントの許可手続き（承認プロンプト等）を経たシェルで行う。MCP や別プロセスで権限制約を回避しない。

SHA-256 の `files` 辞書を持つ manifest（配布フォルダーか導入先にある既存のものを優先し、無ければ作る）がある場合は、このスキルの `scripts/install_manifest.py`（Python 3 標準ライブラリのみ）を使える。既定は変更しない検査のみ。使い方と制限は [references/install.md](references/install.md)。プロジェクト固有の既存インストーラーが適切ならそちらを使う。

## 実行中ゲームへの反映

- **衣装の model / mate / tex 更新**: [references/clothing-runtime.md](references/clothing-runtime.md) を読む。`refresh_mod_files` → `inspect_clothing` → `reload_clothing` の順で通常再読み込みし、Mesh・材質・テクスチャと表示を確認する。ライブ Mesh への一時差し替えは通常ロードの確認とは区別する。
- **SceneEditor の単独モデル・Prefab・ステージ**:
  - 衣装用のツールや `SetProp` を使わない
  - 読み込まれているアセットと配置を特定し、プロジェクトの再ロード API または既存手順を使う
  - 確認項目: 変換 / 複数インスタンス / 材質上書き / 配置 XML の保持
  - 手段が未確認なら導入のみの完了として報告する。全シーン再ロードで未保存の編集を失わない
- **ゲームが停止中またはブリッジに接続できない**: 導入とハッシュ検査を完了し、実機再読み込みは未確認と記録する。勝手にゲームを再起動しない。`mainThreadAlive=false` なら評価キューへの操作を繰り返さない。

## 検証と記録

- 導入前後のハッシュ、退避先、更新したファイル、再読み込みの成否を作業フォルダーへ保存する。コピー成功・通常ロード成功・表示確認済みを分けて記録する。
- 現在の対象・体型・ポーズの範囲で、材質割当、欠落・ピンク表示、対象外衣装の保持を確認する。必要な画角だけ撮影し、カメラを変更した場合は元に戻す。確認していない全体型・全ポーズを合格扱いしない。
- 頂点数や材質枠数だけではモデルの完全一致を証明しない。厳密な形状検証が必要なら保存モデルとの比較を追加し、実機のモーフ適用や座標系の違いを考慮する。
- 実機確認に合わせて README や manifest、ZIP を更新した場合は導入先も最終版へ同期して再照合する。過去の検証値が残る場合は履歴と最新記録を明確にする。
- 停止する条件: コンパイルエラー / ロード失敗 / ハッシュ差異
  - 出た段階で後続操作を止め、原因を確かめて修正する
  - 同じ失敗を根拠なく繰り返さない
  - 途中導入は退避記録から復元できる状態を保ち、報告せず別モデルで上書きしない
- 完了時は反映先と実機確認の範囲を短く伝え、確認画像または検証記録へのリンクを添える。
